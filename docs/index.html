Kamus: HA, DR, RPO/RTO

Empat istilah ini dipakai di seluruh dokumen. Kalau kamu salah paham di sini, semua keputusan teknis di belakangnya ikut salah. Kita pakai analogi dulu, baru definisi teknis.

Target halaman ini

Kamu bisa menjelaskan beda HA dan DR ke rekan non-teknis, dan bisa menyebutkan angka RPO/RTO yang kamu inginkan untuk sistemmu sendiri.

High Availability (HA) — "ada cadangan yang siap gantian"

Bayangkan toko dengan tiga kasir. Kalau satu kasir pingsan, dua lainnya langsung melanjutkan. Pelanggan mungkin menunggu sepuluh detik, tapi toko tidak tutup.

Dalam Postgres: ada satu instance primary yang menerima tulis, dan beberapa replica (standby) yang terus menyalin perubahan dari primary. Kalau primary mati, salah satu replica dipromosikan menjadi primary baru. Proses itu namanya failover.

HA melindungi dari: server mati, proses crash, node di-reboot, disk satu node rusak.

HA tidak melindungi dari: DROP TABLE yang salah, bug aplikasi yang menimpa data, ransomware. Kenapa? Karena replica menyalin semuanya dengan patuh — termasuk perintah penghancurmu, dalam hitungan milidetik.

Disaster Recovery (DR) — "ada arsip di gudang lain"

Kembali ke toko: DR adalah salinan buku catatan penjualan yang disimpan di gudang lain, di kota lain. Kalau tokonya terbakar habis — ketiga kasirnya sekaligus — kamu masih bisa membangun ulang dari catatan itu.

Dalam Postgres: DR adalah backup ke object storage (S3/MinIO) plus arsip WAL (catatan setiap perubahan). Dengan keduanya kamu bisa memulihkan database ke titik waktu mana pun — misalnya kondisi pukul 14:32 kemarin, tepat sebelum DELETE yang keliru. Itu namanya PITR (Point-In-Time Recovery).

Inti perbedaannya

HA menjawab "bagaimana supaya tidak mati?" — jawabannya: replika, otomatis, hitungan detik.
DR menjawab "bagaimana kalau semuanya sudah terlanjur mati/rusak?" — jawabannya: backup, manual, hitungan menit sampai jam.
Kamu butuh keduanya. Punya HA saja bukan berarti punya backup.

RPO — berapa banyak data yang boleh hilang

Recovery Point Objective. Diukur dalam satuan waktu. "RPO 5 menit" artinya: kalau bencana terjadi sekarang, saya menerima kehilangan maksimal 5 menit transaksi terakhir.

RPOCara mencapainyaHarganya
0 detikReplikasi sinkron — primary tidak menganggap tulis selesai sebelum replica mengonfirmasiSetiap COMMIT jadi lebih lambat; kalau replica lambat, primary ikut lambat
< 1 menitReplikasi asinkron + arsip WAL kontinu ke S3Murah, umum dipakai
24 jamBackup harian saja, tanpa arsip WALSangat murah, dan hampir selalu tidak cukup

RTO — berapa lama boleh mati

Recovery Time Objective. "RTO 15 menit" artinya: dari saat bencana sampai layanan kembali normal, maksimal 15 menit.

Ini yang sering dilupakan: RTO ditentukan oleh kecepatan restore, bukan kecepatan backup. Backup 500 GB yang selesai dalam 20 menit bisa butuh 3 jam untuk di-restore. Kalau kamu belum pernah mengukurnya, kamu tidak tahu RTO-mu — kamu cuma berharap.

Kalimat yang harus kamu ingat

Backup yang belum pernah di-restore bukanlah backup. Itu cuma file besar yang memberimu perasaan aman. Di Fase 6 kita jadwalkan latihan restore rutin, karena inilah satu-satunya cara membuktikan angka RTO-mu.

IstilahArti sederhana

Langkah 2 — Cluster lokal dengan kind

Kita buat cluster 4 node: 1 control-plane + 3 worker. Tiga worker penting karena nanti kita butuh menyebar replika Postgres ke node berbeda dan mensimulasikan kematian satu node.

  1. Buat file konfigurasi

    mkdir -p ~/lab-k8s && cd ~/lab-k8s
cat > kind-config.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: lab
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
      - containerPort: 443
        hostPort: 443
  - role: worker
  - role: worker
  - role: worker
EOF

  2. Jalankan cluster

    kind create cluster --config kind-config.yaml

    Proses pertama kali butuh 2–5 menit karena mengunduh image node.

  3. Verifikasi

Kenapa :latest itu bug

Tag seperti postgres:16 bisa menunjuk ke image yang berbeda minggu depan. Kalau pod-mu restart dan menarik image baru yang tidak kompatibel dengan file data di disk, database bisa gagal start. Untuk database, selalu kunci ke versi minor spesifik (postgres:16.4), dan di produksi kunci ke digest (postgres@sha256:…).

Lab 0 — Rasakan data yang hilang

Tujuan lab ini terdengar aneh: kita sengaja menghilangkan data supaya kamu punya ingatan fisik tentang apa yang dilindungi oleh PersistentVolume nanti.

  1. Bangun image Postgres kustom dengan satu extension tambahan

    mkdir -p ~/lab-k8s/lab0 && cd ~/lab-k8s/lab0

cat > Dockerfile <<'EOF'
FROM postgres:16.4-bookworm

RUN apt-get update \
 && apt-get install -y --no-install-recommends postgresql-16-cron \
 && rm -rf /var/lib/apt/lists/*

RUN echo "shared_preload_libraries='pg_cron'" >> /usr/share/postgresql/postgresql.conf.sample \
 && echo "cron.database_name='appdb'"      >> /usr/share/postgresql/postgresql.conf.sample
EOF

docker build -t pg-lab0:16.4 .

  2. Jalankan dengan named volume

Control plane — otaknya

KomponenTugasnya, dalam satu kalimat

Yang terjadi saat kamu mengetik kubectl apply

  1. kubectl mengirim YAML-mu ke kube-apiserver.
  2. API server memvalidasi, lalu menulis "keinginan" itu ke etcd.
  3. Controller yang relevan melihat ada keinginan baru yang belum terpenuhi.
  4. Controller membuat objek turunan (misalnya Deployment → ReplicaSet → Pod).
  5. Scheduler melihat Pod yang belum punya node, lalu memilihkan node.
  6. Kubelet di node itu melihat ada tugas untuknya, lalu menjalankan container.

Tidak ada satu pun langkah di atas yang "memerintah". Semua bekerja dengan mengamati dan menyesuaikan. Itulah reconciliation loop.

Fase 1 · Scheduling, Jaringan & Keamanan

Halaman ini menentukan apakah database-mu stabil atau terus-menerus rewel. Kebanyakan masalah "Postgres di Kubernetes lambat" berakar pada dua hal yang dibahas di sini: limits yang salah, dan penempatan pod yang tidak diatur.

Target halaman ini

Kamu bisa memastikan tiga replika database berada di tiga node berbeda, tidak pernah ter-throttle CPU, dan tidak semuanya ikut mati saat satu node di-drain.

Requests, limits, dan kenapa CPU limit membunuh database

requests = jaminan minimal. Scheduler memakai angka ini untuk memilih node.
limits = pagar maksimal. Kalau dilewati: memori → pod dibunuh (OOMKilled); CPU → pod di-throttle, dipaksa berhenti sebentar.

Aturan yang tidak boleh dilupakan

Jangan set CPU limit pada pod database. Throttling CPU bekerja per periode 100 ms. Kalau query-mu sedang di tengah pemindaian dan kernel menghentikannya paksa, latency melonjak tak terduga dan sulit didiagnosis — grafiknya terlihat seperti "database kadang lambat tanpa sebab". Punya tetangga berisik masih lebih baik daripada throttling.

Yang benar untuk database: requests.cpu tinggi (biar dapat node yang lapang), tanpa limits.cpu, dan limits.memory = requests.memory supaya QoS-nya Guaranteed.

resources:
  requests:
    cpu: "2"
    memory: "8Gi"
  limits:
    memory: "8Gi"   # sama dengan requests → QoS Guaranteed
    # cpu sengaja TIDAK diisi
QoS classSyaratNasib saat node kehabisan memori
Guaranteedrequests = limits untuk semua resource yang diisiDibunuh terakhir — inilah yang kita mau untuk database
Burstablerequests < limitsDibunuh setelah BestEffort
BestEfforttidak ada requests/limitsDibunuh pertama

podAntiAffinity — sebar replika, jangan menumpuk

Tanpa ini, ketiga replika Postgres-mu bisa saja dijadwalkan di node yang sama. Satu node mati, semuanya hilang, dan HA-mu ternyata cuma hiasan.

required… = wajib; kalau tidak ada node yang cocok, pod tetap Pending. preferred… = diusahakan tapi boleh dilanggar. Untuk lab 3 node, pakai preferred supaya tidak macet; untuk produksi, required.

Operator pattern — kenapa database butuh operator

StatefulSet cuma bisa "menjalankan proses secara tertib". Ia tidak tahu apa itu primary, tidak tahu cara mempromosikan replika, tidak tahu cara mengarsipkan WAL.

Operator = CRD (jenis objek baru, misalnya Cluster milik CloudNativePG) + controller yang tahu cara merawat objek itu. Controller-nya menjalankan reconciliation loop yang sama seperti Kubernetes: melihat kondisi nyata, membandingkan dengan keinginanmu, bertindak.

  StatefulSet 3 replika            kind: Cluster
  + Service                        spec:
  + ConfigMap postgresql.conf        instances: 3
  + Secret                           backup: { ... }
  + CronJob backup                 → operator yang mengurus sisanya,
  + skrip failover buatan sendiri    termasuk failover otomatis
  + skrip promote buatan sendiri
  ← kamu yang jadi operatornya

MVCC dan bloat — penyebab masalah nomor satu

Saat kamu menjalankan UPDATE, Postgres tidak mengubah baris yang ada. Ia menulis versi baru dan menandai versi lama sebagai kedaluwarsa. Versi lama tetap menghuni disk sampai autovacuum membersihkannya. Ruang mati itulah bloat.

psql "$PGURL" <<'EOF'
CREATE TABLE barang(id serial PRIMARY KEY, nama text, harga int);
INSERT INTO barang(nama, harga)
  SELECT 'item-'||g, (random()*1000)::int FROM generate_series(1,500000) g;

-- lihat ukuran awal
SELECT pg_size_pretty(pg_total_relation_size('barang')) AS ukuran;

-- matikan autovacuum untuk tabel ini supaya bloat terlihat jelas
ALTER TABLE barang SET (autovacuum_enabled = false);

-- update seluruh tabel lima kali
UPDATE barang SET harga = harga + 1;
UPDATE barang SET harga = harga + 1;
UPDATE barang SET harga = harga + 1;
UPDATE barang SET harga = harga + 1;
UPDATE barang SET harga = harga + 1;

SELECT pg_size_pretty(pg_total_relation_size('barang')) AS ukuran_setelah;
EOF

Datanya sama banyak. Ukurannya lima kali lipat. Setiap query yang memindai tabel ini sekarang membaca lima kali lebih banyak halaman disk.

psql "$PGURL" <<'EOF'
-- metrik yang harus kamu pantau di produksi
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0*n_dead_tup/NULLIF(n_live_tup+n_dead_tup,0),1) AS persen_mati,
       last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5;

VACUUM (VERBOSE, ANALYZE) barang;
SELECT pg_size_pretty(pg_total_relation_size('barang'));

-- kembalikan autovacuum, dan buat lebih agresif untuk tabel besar
ALTER TABLE barang SET (
  autovacuum_enabled = true,
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000

Kenapa tabel besar butuh setelan sendiri

Default autovacuum_vacuum_scale_factor = 0.2 berarti autovacuum baru jalan setelah 20% baris mati. Pada tabel 100 juta baris, itu 20 juta tuple mati sebelum pembersihan dimulai — terlambat. Untuk tabel besar, turunkan ke 0,01–0,02 per tabel, bukan secara global.

Transaction ID wraparound

Postgres memakai penghitung transaksi 32-bit. Kalau autovacuum tertinggal terlalu jauh — biasanya karena ada transaksi menganggur yang terbuka berhari-hari — penghitungnya bisa mendekati batas dan Postgres akan menolak semua transaksi tulis untuk menyelamatkan diri. Ini bukan teori; ini penyebab beberapa insiden besar yang terkenal. Pantau age(datfrozenxid) dan pasang alert.

SELECT datname, age(datfrozenxid) AS umur_xid
FROM pg_database ORDER BY 2 DESC;
-- alert kalau melewati ~200 juta; batas kerasnya sekitar 2 miliar

Tentang walStorage

Memisahkan WAL ke volume tersendiri punya dua manfaat: pola tulis WAL (sekuensial, terus-menerus) tidak berebut dengan pola tulis data (acak), dan kalau volume data penuh, WAL masih punya ruang sehingga database tidak berhenti total. Di produksi, taruh di disk fisik berbeda kalau bisa.

Fase 3 · High Availability & Failover

Cluster tiga instance saja belum berarti HA. HA berarti: saat primary mati, sistem pulih sendiri dalam waktu yang kamu ketahui angkanya, dan kamu bisa membuktikan tidak ada data yang hilang. Di halaman ini kita bunuh primary berkali-kali sambil mengukur.

Target halaman ini

Kamu punya angka nyata: berapa detik downtime saat failover, dan berapa transaksi yang hilang dengan replikasi asinkron versus sinkron. Bukan perkiraan — angka hasil pengukuranmu sendiri.

Bagaimana CloudNativePG melakukan failover

  1. Operator terus memeriksa kesehatan setiap instance lewat instance manager di dalam pod.
  2. Primary berhenti merespons. Operator menunggu selama failoverDelay (default 0 detik) untuk menghindari reaksi berlebihan terhadap gangguan sesaat.
  3. Operator memilih standby dengan LSN paling maju — yang datanya paling lengkap.
  4. Standby itu dipromosikan menjadi primary. Timeline Postgres bertambah satu.
  5. Service -rw dialihkan ke pod baru.
  6. Bekas primary, saat hidup lagi, dibuat menyusul primary baru (kalau perlu, disalin ulang).

Aplikasimu tidak perlu tahu apa-apa. Ia tetap terhubung ke pg-lab-rw.db.svc.cluster.local. Yang ia rasakan hanya koneksi terputus sebentar — jadi pastikan driver aplikasimu bisa menyambung ulang otomatis.

Uji 1 — Failover asinkron, ukur downtime

  1. Siapkan penulis yang mencatat setiap detik

    kubectl -n db port-forward svc/pg-lab-rw 5432:5432 >/dev/null 2>&1 &
sleep 3
PGPASS=$(kubectl -n db get secret pg-lab-app -o jsonpath='{.data.password}' | base64 -d)
export PGURL="postgresql://appuser:$PGPASS@localhost:5432/appdb"

psql "$PGURL" -c "CREATE TABLE IF NOT EXISTS detak(id bigserial PRIMARY KEY, saat timestamptz DEFAULT now());"

while true; do
  if psql "$PGURL" -q -c "INSERT INTO detak DEFAULT VALUES;" 2>/dev/null; then
    printf "."
  else
    printf "X"
  fi
  sleep 0.5
done

    Titik berarti tulis berhasil, X berarti gagal. Deretan X adalah downtime-mu, terlihat langsung di layar.

  2. Bunuh primary

    PRIMARY=$(kubectl -n db get cluster pg-lab -o jsonpath='{.status.currentPrimary}')
echo "primary sekarang: $PRIMARY"

date +%T.%3N
kubectl -n db delete pod $PRIMARY --grace-period=0 --force

  3. Amati dan catat

    kubectl -n db get events --sort-by=.lastTimestamp | tail -15
kubectl cnpg status pg-lab -n db | head -20
    ...........XXXXXXXXXX.................
             ^^^^^^^^^^
             ± 5 detik downtime

    Tulis angkanya sekarang: downtime failover asinkron di lab saya = ______ detik. Bandingkan dengan RTO yang kamu tulis di halaman 02.

  4. Periksa apakah ada data yang hilang

    psql "$PGURL" -c "
SELECT count(*) AS total,
       max(saat) AS terakhir,
       now() - max(saat) AS selisih
FROM detak;"

-- cari lubang pada urutan id: bukti transaksi yang hilang
psql "$PGURL" -c "
SELECT id + 1 AS mulai_hilang, next_id - 1 AS akhir_hilang
FROM (SELECT id, lead(id) OVER (ORDER BY id) AS next_id FROM detak) t
WHERE next_id - id > 1;"
    Yang mungkin kamu lihat

    Dengan replikasi asinkron, mungkin ada beberapa transaksi yang sudah di-COMMIT di primary lama tapi belum sampai ke standby. Transaksi itu hilang saat failover. Inilah wujud nyata dari "RPO tidak nol". Kalau kamu tidak boleh kehilangan satu transaksi pun, lanjut ke uji berikutnya.

Uji 2 — Replikasi sinkron, RPO nol

spec:
  postgresql:
    synchronous:
      method: any          # kuorum: berapa pun dari daftar kandidat
      number: 1            # minimal 1 standby harus mengonfirmasi
      # dataDurability: required   # default: primary berhenti menulis
      #                            # kalau tidak ada standby yang sehat
Catatan versi

Bagian postgresql.synchronous tersedia pada CNPG 1.24 ke atas. Pada versi lama, setelan yang setara adalah minSyncReplicas dan maxSyncReplicas di level spec. Cek dokumentasi versi operator yang kamu pasang; jangan menyalin tutorial lama mentah-mentah.

Sekarang ulangi Uji 1 dari awal. Perhatikan dua hal:

  • Downtime biasanya sedikit lebih lama (proses promosi lebih hati-hati).
  • Query pencari lubang seharusnya tidak menemukan apa pun. Itulah RPO nol.
Sisi gelap replikasi sinkron

Dengan number: 1 dan hanya satu standby yang tersisa hidup, kalau standby itu ikut bermasalah, primary berhenti menerima tulis — karena tidak ada yang bisa mengonfirmasi. Ini pilihan sadar: lebih baik berhenti daripada kehilangan data. Ujilah supaya kamu tidak kaget:

kubectl -n db delete pod pg-lab-2                  # bunuh satu-satunya standby
# amati jendela 1: penulisan berhenti sampai standby kembali

Uji 3 — Switchover terencana

Failover itu kecelakaan. Switchover itu keputusan — dipakai saat kamu mau maintenance node, dan hampir tanpa kehilangan data.

kubectl cnpg status pg-lab -n db | grep "Primary instance"

kubectl cnpg promote pg-lab pg-lab-3 -n db

sleep 15
kubectl cnpg status pg-lab -n db | grep "Primary instance"

Amati jendela 1: harusnya cuma satu atau dua X, jauh lebih pendek dari failover.

Uji 4 — Node mati, bukan cuma pod

Menghapus pod itu kematian yang sopan. Node yang mati mendadak lebih realistis: kubelet berhenti melapor, dan Kubernetes butuh waktu untuk menyimpulkan node itu benar-benar hilang.

# untuk k3s: sudo systemctl stop k3s  (jalankan di VPS terkait)

watch -n2 'kubectl -n db get pod -o wide; echo; kubectl get nodes'
Yang akan kamu lihat, dan kenapa

Node butuh sekitar 40 detik untuk ditandai NotReady, lalu sekitar 5 menit lagi sebelum pod-nya dianggap hilang dan dijadwalkan ulang (pod-eviction-timeout). Untungnya CNPG tidak menunggu selama itu — ia mendeteksi primary tidak responsif dan mempromosikan standby jauh lebih cepat. Ukur sendiri dan catat: downtime failover node-down = ______ detik.

sleep 40
kubectl cnpg status pg-lab -n db

Bukti Lulus

HA selesai kalau

  • Kamu punya empat angka di tabel di atas, hasil pengukuran sendiri.
  • Kamu sudah membuktikan bahwa asinkron bisa kehilangan transaksi dan sinkron tidak.
  • Kamu sudah mengalami primary berhenti menulis karena tidak ada standby sinkron — dan paham kenapa itu perilaku yang benar.
  • Kamu bisa menjelaskan beda failover dan switchover kepada rekan kerja.
  • Kamu tahu apa yang terjadi kalau node yang menjalankan primary mati saat ini juga.

Fase 3 · Backup, PITR & Disaster Recovery

Kalau kamu hanya punya waktu untuk membaca satu halaman dari seluruh dokumen ini, baca halaman ini. HA melindungimu dari perangkat keras yang rusak. Halaman ini melindungimu dari dirimu sendiri.

Target halaman ini

Kamu bisa memulihkan database ke kondisi tepat sebelum sebuah DELETE yang keliru — dan kamu tahu berapa menit prosesnya, karena kamu sudah mengukurnya.

Cara kerja backup CloudNativePG

  Primary Postgres
        |
        |-- base backup  ---------→  s3://backup/pg-lab/base/…
        |   (salinan penuh berkala)
        |
        '-- WAL archiving --------→  s3://backup/pg-lab/wals/…
            (setiap segmen WAL, terus-menerus)

  Pemulihan = base backup terakhir + putar ulang WAL
              sampai titik waktu yang kamu minta

Karena WAL diarsipkan terus-menerus, kamu bisa berhenti di detik mana pun antara backup penuh terakhir sampai sekarang. Itulah PITR.

Connection pooling — kenapa wajib

Setiap koneksi Postgres = satu proses OS dengan memori sendiri. Aplikasi serverless atau yang punya banyak replika bisa membuka ratusan koneksi; sebagian besar menganggur. Postgres menghabiskan waktu mengelola proses, bukan menjawab query.

PgBouncer duduk di depan, memelihara sedikit koneksi nyata ke Postgres, dan memberi ilusi banyak koneksi ke aplikasi.

Jebakan transaction mode — ini akan menggigitmu saat migrasi Supabase

Dalam transaction mode, hal-hal berikut rusak: prepared statement (yang dipakai otomatis oleh banyak driver), SET di level sesi, LISTEN/NOTIFY, advisory lock yang dipegang lintas transaksi, dan tabel temporer.

Perbaikannya di sisi driver:

JDBC        : prepareThreshold=0
psycopg2/3  : prepare_threshold=None
asyncpg     : statement_cache_size=0
node-postgres: hindari prepared statement bernama
Prisma      : pgbouncer=true pada connection string
SQLAlchemy  : poolclass=NullPool + prepare_threshold=None

Kalau aplikasimu tidak bisa disesuaikan, pakai session mode. Lebih lambat, tapi jalan.

Fase 4 · MongoDB di Kubernetes

Kalau tujuan utamamu keluar dari Supabase, fase ini boleh ditunda ke belakang Fase 7. Tapi konsep di sini — kuorum, write concern, election — memperkuat pemahamanmu tentang HA secara umum.

Target halaman ini

Kamu bisa membuktikan secara empiris bahwa w: 1 kehilangan write saat failover, dan w: "majority" tidak.

Yang berbeda dari Postgres

KonsepPenjelasan
Replica setKumpulan node: satu Primary, sisanya Secondary. Election memilih primary baru saat yang lama hilang. Jumlah ganjil (3, 5) supaya kuorum jelas. Hindari Arbiter kalau bisa — ia ikut memilih tapi tidak menyimpan data, jadi tidak menambah durabilitas.
OplogCapped collection berisi riwayat operasi. Secondary membacanya untuk menyusul. Oplog window = berapa lama riwayat tersimpan. Kalau secondary mati lebih lama dari window, ia tidak bisa menyusul dan harus disalin ulang dari nol.
writeConcernw:1 = primary saja mengakui. w:"majority" = mayoritas node mengakui. j:true = sudah tertulis ke journal di disk. Ini setara synchronous_commit di Postgres.
Aturan ESRUrutan field pada compound index: Equality dulu, lalu Sort, lalu Range. Salah urutan = index tidak terpakai maksimal.
ShardingPelajari konsepnya, jangan implementasikan. Kamu hampir pasti belum butuh. Baru relevan kalau working set melebihi RAM satu node.

Empat hal yang harus dipahami sebelum menyentuh apa pun

KonsepPenjelasan
ORDER BYMenentukan urutan fisik data di disk dan sparse primary index. Ini bukan sekadar pengurutan hasil — ini struktur penyimpanan. Urutkan dari kardinalitas rendah ke tinggi. Salah pilih = query lambat berkali-kali lipat, dan memperbaikinya berarti membangun ulang tabel.
PARTITION BYAnti-pattern paling umum: partisi terlalu halus (per jam, atau per user). Aturan praktis toYYYYMM(tanggal) — target puluhan sampai ratusan partisi, bukan ribuan. Ribuan partisi membuat merge tidak pernah menyusul dan cluster jadi tidak sehat.

Shard vs ReplicaShard = skala (data dibagi). Replica = ketersediaan (data disalin). Mulai dengan 1 shard × 2 replika. Sharding hanya kalau data melebihi kapasitas satu node.

Yang TIDAK berguna

kind: PrometheusRule
metadata:
  name: postgres-penting
  namespace: monitoring
  labels: { release: kps }
spec:
  groups:
    - name: postgres
      rules:

        - alert: ReplikasiTertinggal
          expr: cnpg_pg_replication_lag > 30
          for: 5m
          labels: { severity: warning }
          annotations:
            summary: "Replika {{ $labels.pod }} tertinggal > 30 detik"

        - alert: ArsipWALGagal
          expr: cnpg_collector_pg_wal_archive_status{status="failed"} > 0
          for: 5m
          labels: { severity: critical }
          annotations:
            summary: "Arsip WAL gagal — PITR TIDAK berfungsi saat ini"

        - alert: BackupTerlaluLama
          expr: time() - cnpg_collector_last_available_backup_timestamp > 90000
          labels: { severity: critical }
          annotations:
            summary: "Backup terakhir lebih dari 25 jam yang lalu"

        - alert: DiskHampirPenuh
          expr: |
            (kubelet_volume_stats_available_bytes{namespace="db"}
             / kubelet_volume_stats_capacity_bytes{namespace="db"}) < 0.25
          for: 10m
          labels: { severity: warning }
          annotations:
            summary: "PVC {{ $labels.persistentvolumeclaim }} sisa < 25%"

        - alert: DiskPenuhDalam4Jam
          expr: |
            predict_linear(
              kubelet_volume_stats_available_bytes{namespace="db"}[1h], 4*3600
            ) < 0
          for: 15m
          labels: { severity: critical }
          annotations:
            summary: "Disk diperkirakan penuh dalam 4 jam — bertindak sekarang"

        - alert: KoneksiHampirHabis
          expr: |
            sum(cnpg_backends_total) by (pod)
            / max(cnpg_pg_settings_setting{name="max_connections"}) by (pod) > 0.8
          for: 5m
          labels: { severity: warning }
          annotations:
            summary: "Koneksi di {{ $labels.pod }} melewati 80% kapasitas"

        - alert: TransaksiMenganggurTerlaluLama
          expr: cnpg_backends_max_tx_duration_seconds > 3600
          for: 10m
          labels: { severity: warning }
          annotations:
            summary: "Ada transaksi terbuka > 1 jam — memblokir autovacuum"

        - alert: ClusterTidakSehat
          expr: cnpg_pg_replication_in_recovery{} == 1
                and on(namespace) cnpg_pg_replication_streaming_replicas < 1

Tiga opsi arsitektur

Opsi A — Supabase penuh, self-hosted di Kubernetes

Semua komponen dipindahkan. Aplikasi hampir tidak perlu diubah; cukup ganti URL dan kunci.

Plus: perubahan kode paling sedikit, fitur tetap lengkap.
Minus: kamu sekarang mengoperasikan sembilan layanan, bukan satu. Chart komunitas supabase-community/supabase-kubernetes dipelihara komunitas, bukan resmi, dan sering tertinggal versi upstream. Kamu akan menjadi maintainer de-facto-nya.

Opsi B — Hanya Postgres, ganti seluruh lapisan atas

Postgres di CloudNativePG. Auth pakai solusi lain. API kamu tulis sendiri.

Plus: beban operasional jangka panjang paling ringan; tidak terkunci pada apa pun.
Minus: pekerjaan aplikasi paling banyak di awal. Kalau aplikasimu banyak memakai RLS lewat PostgREST, kamu harus memindahkan logika itu ke API buatanmu.

Opsi C — Hybrid (rekomendasi untuk kebanyakan tim)

Self-host tiga komponen inti: Postgres + PostgREST + GoTrue. Buang Realtime, Storage, dan Edge Functions kalau pemakaiannya ringan atau bisa diganti.

Plus: titik seimbang. Aplikasi berubah sedikit, layanan yang harus dirawat cuma tiga.
Minus: tetap perlu memutuskan pengganti untuk fitur yang dibuang.

Jangan memilih sekarang

Pilih setelah audit di halaman berikutnya. Banyak tim mengira mereka memakai Realtime, lalu menemukan hanya satu channel dipakai untuk satu notifikasi yang bisa diganti polling. Sebaliknya, ada tim yang mengira Storage-nya kecil, ternyata isinya 400 GB.

Ekstensi Supabase — blocker paling sering

  2. Bangun image kustom yang meng-compile extension yang kamu butuhkan.
  3. Hilangkan ketergantungannya dari aplikasi.
Selesaikan ini di minggu pertama, bukan di hari cutover

Ini blocker nomor satu dalam migrasi keluar dari Supabase. Restore schema akan gagal di baris CREATE EXTENSION — dan kalau kamu baru menemukannya pukul 23:00 di malam cutover, kamu akan membuat keputusan buruk di bawah tekanan.

       pg_size_pretty(pg_total_relation_size(relid)) AS ukuran,

SELECT t.table_schema, t.table_name

Fase 7 Kerja: 3–7 hari Paling sering gagal: auth

Fase 7 · Auth, Storage & Realtime

Database sudah pindah. Sekarang bagian yang tidak ada di database — dan inilah yang biasanya memakan 80% waktu migrasi meskipun cuma 20% dari perencanaan awal.

Target halaman ini

User bisa login di sistem barumu dengan password lama mereka, berkas lama bisa diunduh, dan berkas baru bisa diunggah.

Auth / JWT — bagian paling sensitif

Kabar baiknya

Tabel auth.users ikut terbawa oleh dump atau replikasi. Password disimpan sebagai hash bcrypt, dan hash itu tetap valid selama GoTrue di sisi target memakai algoritma yang sama. User tidak perlu reset password.

Kabar yang perlu keputusan

JWT secret menentukan nasib semua sesi aktif

Kalau kamu memakai secret yang sama, semua token yang sudah beredar tetap valid — user tidak terusir. Kalau kamu merotasinya, semua user logout serentak.

Merotasi sering justru pilihan yang lebih bersih dan lebih aman: secret lama pernah dipegang pihak ketiga (Supabase), dan logout massal yang terencana lebih baik daripada kebocoran yang tidak terdeteksi. Tapi putuskan sekarang, bukan saat cutover, karena keputusan ini mengubah isi pengumuman ke pengguna.

Kalau project-mu sudah memakai asymmetric key

Supabase versi baru memakai ES256/RS256 dengan endpoint JWKS, bukan lagi secret simetris. Kalau begitu, konfigurasikan GoTrue target dengan key pair yang sama, atau rencanakan re-login massal. Cek di dashboard: Project Settings → API → JWT Keys.

Batas waktu rollback

Rollback mudah selama belum ada penulisan baru di sistem baru. Begitu pengguna mulai membuat data di target, rollback berarti kamu harus memindahkan data itu kembali — jauh lebih rumit. Karena itu tentukan tenggat: misalnya, keputusan rollback hanya boleh diambil dalam 60 menit pertama. Lewat itu, jalan satu-satunya adalah memperbaiki ke depan.

  • Semua alert aktif dan sudah terverifikasi jalurnya.
  • Jangan hapus project Supabase. Tunggu minimal 30 hari. Biayanya jauh lebih murah daripada penyesalan.

Catatan penutup

Dokumen ini mengasumsikan kamu ingin menguasai domainnya, bukan sekadar menyelesaikan satu migrasi.

Kalau tujuanmu murni "keluar dari Supabase secepatnya", jalur tercepat tetap: halaman 09 (Postgres fundamental) + halaman 18–24 (migrasi), dengan Postgres di VM biasa memakai pgBackRest. Sekitar tiga minggu, bukan enam belas. Kubernetes bisa menyusul nanti, setelah sistemnya stabil dan kamu punya ruang bernapas.

Urutan fase juga bisa disesuaikan. Kalau ClickHouse tidak mendesak, geser halaman 15 ke belakang halaman 24. Yang tidak boleh dilewati hanya dua: halaman 08 (storage) dan halaman 16–17 (day-2 ops). Dua bagian itu yang paling sering diabaikan, dan paling sering jadi penyebab insiden.

Satu hal terakhir

Ukuran keberhasilanmu bukan "sistemnya jalan". Sistem yang jalan itu mudah. Ukurannya adalah: saat sesuatu rusak, kamu tahu apa yang terjadi, tahu berapa lama pulihnya, dan bisa membuktikannya dengan angka. Semua lab di dokumen ini dirancang untuk membangun kemampuan itu, bukan untuk membangun demo yang bagus.
